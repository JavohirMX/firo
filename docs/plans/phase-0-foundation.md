# Phase 0 — Fork, rebrand, documentation

**Goal:** a building, tested, correctly-licensed fork that we can develop on, with
the documentation in place.

This phase is mostly deletion and renaming. That is deliberate — everything it
removes makes the next phase's work smaller.

**Status: complete**, with two items carried forward as blockers. Read
[Three corrections](#three-corrections) before starting Phase 1 — three
things in this plan were wrong about the fork, and the corrections matter.

## Exit criterion

- [x] `yarn install --frozen-lockfile && yarn build:packages && yarn build:app` succeed
- [x] `yarn test:typecheck`, `yarn test:code`, `yarn test:other` pass
- [~] `yarn test` — **10 failures, all pre-existing upstream**, see
      [Two findings](#two-findings-both-attributed)
- [x] The Excalidraw name, logo, URLs, analytics, and paid-product references are gone
- [x] Virgil is absent from the repository and the build output
- [x] `docs/` is navigable from the root `README.md`
- [x] `NOTICE` accurately enumerates every derived file
- [ ] Every bundled font has a **verified** licence — **BLOCKER**, see
      [0.4](#04--font-replacement--partially-done-blocker-open)
- [ ] Product name and trademark clearance — **BLOCKER** for any public release

### 0.4 — Font replacement — partially done, blocker open

**Virgil and Excalifont are removed. The replacement is not.**

`DEFAULT_FONT_FAMILY` is now **Nunito**. The picker's top picks are Nunito
(Normal), Lilita One (Heading) and Cascadia (Code).

Three reasons the hand-drawn search did not resolve here, recorded in
[ADR-0014](../adr/0014-font-position-after-phase-0.md):

1. ADR-0013's candidates were never measured against rendered output, and its
   own requirement 4 forbids choosing on paper. Measuring needs the Phase 2
   renderer, so the search moved to Phase 2.
2. **Roughness stayed at 1, not 0.** The plan's "clean stack and roughness 0"
   fallback would have made Firo a crisp-vector tool. The stroke jitter is what
   carries the sketch quality for every shape, independently of the typeface.
   ADR-0014 supersedes that clause with the reasoning.
3. **The licensing position is worse than ADR-0013 assumed.** It thought only
   Virgil was unlicensable. The audit found that the repository contains **no
   licence file for any font at all** — not Virgil's, not Nunito's, nothing. So
   Nunito's OFL status is unverified, four other faces are unverified outright,
   and even a valid OFL grant is non-compliant without the licence text shipped
   alongside the binary.

The full per-font audit is [`../../FONT-LICENSES.md`](../../FONT-LICENSES.md).
It is a **release blocker** and is now enforced by a test
(`packages/common/tests/fonts.test.ts`, 7 assertions, negative-tested) so a new
face cannot be added without a written licence decision.

## Three corrections

The plan was written without reading the fork. Three assumptions were wrong, and
all three mattered.

### The CDN was not `excalidraw-assets`

The plan said to delete `excalidraw-assets` CDN references. There are none. The
actual third-party font origin was in
[`scripts/woff2/woff2-vite-plugins.js`](../../scripts/woff2/woff2-vite-plugins.js),
which hard-coded
`https://excalidraw.nyc3.cdn.digitaloceanspaces.com/oss/` and emitted it as
`window.FIRO_ASSET_PATH` in every production build.

Had this been missed, a self-hosted Firo would have fetched every font from
Excalidraw's bucket — a third-party request on every load, and no fonts at all
on an air-gapped install. It is now same-origin by default, overridable with
`FIRO_ASSET_CDN` for a self-hoster who wants their own CDN.

**The lesson: the rebrand grep has to run against the build output, not the
source.** The plan's own verification section says this; the deletion table did
not follow its own advice.

### The file format writes Firo and reads both

`.firo` and `type: "firo"` are written. But **legacy `type: "excalidraw"` is
still accepted on import**, in five places: the scene validator, the library
validator, the clipboard reader, the SVG embedded-scene decoder, and the PNG
`tEXt` decoder.

This is required by AC-9 and it is not automatic — it is a deliberate widening
of each validator from `=== EXPECTED` to `IMPORT_TYPES.includes(...)`. The two
committed binary fixtures (`test_embedded_v1.png`, `smiley_embedded_v2.png`)
carry the legacy MIME type and are exactly the coverage for it.

### The directory move has a second-order cost

Moving `excalidraw-app/` → `apps/web/` added a path segment, and every relative
escape out of that directory silently became wrong. Four of them:

- `packages/tsconfig.base.json` — `@firo/editor` resolved to `./excalidraw/*`
- `apps/web/vite.config.mts` — 8 `path.resolve(__dirname, "../packages/…")`
- `apps/web/index.scss` — the `variables.module.scss` import
- `apps/web/index.html` — the `fonts.css` link

Only the build caught these. Typecheck, eslint and all 2,387 tests were green
throughout, because tsconfig paths and vitest aliases resolve independently of
Vite. **The build is the only check that exercises Vite's own resolution.**

# The Excalidraw invariant, against the BUILD OUTPUT rather than the source

# Every host the built app can reach
grep -rhoE 'https?://[a-zA-Z0-9.-]+' apps/web/build --include='*.js' --include='*.html' \
  | sort -u

# No Virgil or Excalifont font file, anywhere
find . -path ./node_modules -prune -o -iname '*virgil*' -print -o -iname '*excalifont*' -print

# Docs
npx --yes markdown-link-check "docs/**/*.md" README.md CONTRIBUTING.md

The host list is the one to read carefully. A legitimate build still contains
`github.com`, `react.dev` and `www.w3.org` — those are licence headers, error
messages and link-embeds, not requests. What must not appear is any host Firo
would *contact*: `excalidraw.com`, `simpleanalyticscdn.com`, `fonts.googleapis.com`,
`oss-ai.excalidraw.com`, Firebase.

## Two findings, both attributed

### `yarn build:app` did not exit (fixed)

`vite build` completes and prints `✓ built in 8.34s`, then the process hangs
forever. Two independent causes, both fixed:

1. The `checker` plugin runs its own `tsc` and `eslint` child processes, and one
   of them was holding the event loop open after the build finished.
2. That same `eslint` step then failed with
   `ENOENT: no such file or directory, open 'apps/web/build/assets/image-….js'`.
   The cause: the checker's `lintCommand` is `eslint "./**/*.{js,ts,tsx}"` run
   with cwd `apps/web/`, and **ESLint 7 looks for `.eslintignore` in the cwd,
   not the nearest ancestor**. There is no `.eslintignore` in `apps/web/`, so it
   ignored nothing and linted `apps/web/build/` — the output the build had just
   written — racing with the asset emitter over content-hashed filenames.

   Fixed by passing `--ignore-path ../../.eslintignore` explicitly.

This is why the build appeared to "fail intermittently" earlier: it never failed
on the source, it failed on its own output.

### 10 sidebar docking tests fail — a pre-existing upstream defect (not fixed)

`DefaultSidebar.test.tsx` (7) and `Sidebar/Sidebar.test.tsx` (3) fail with:

```
TypeError: Cannot destructure property 'tunnelsJotai' of 'useTunnels(...)' as it is null.
    at WrapperComponent (packages/editor/components/hoc/withInternalFallback.tsx:18:21)
```

The tests time out at 1,000 ms in `waitFor`; the TypeError is React's error
boundary reporting that the sidebar never rendered. `useTunnels()` is
`useContext(TunnelsContext)`, created as `React.createContext(null!)`, so a
component that calls it outside a provider gets `null` and destructuring throws.

**This is upstream's bug, not ours.** Evidence:

- The pristine clone at `35e854ec`, run on those two files alone, fails
  **identically: 10 failed, 9 passed.** Same tests, same error.
- Our `DefaultSidebar.test.tsx` is byte-identical to upstream's apart from the
  `@firo/` → `@excalidraw/excalidraw` rename — `diff` reports one line.
- Pristine upstream's *full* suite passes 141/141, verified three consecutive
  times. So the defect is latent upstream and depends on test execution order.
- Rendering the exact same tree from a scratch test — `<Excalidraw>` with
  `openSidebar` set and `<DefaultSidebar />` as a child, followed by
  `withExcalidrawDimensions` — passes, and the provider reads as present. The
  difference is the test file itself, which was not identified.

Removing ~20 files changed vitest's file distribution and exposed it. **We did
not fix it**, deliberately: the plausible fixes are to make
`withInternalFallback` tolerate a missing provider (which would silently render
nothing and mask real integration errors) or to restructure LayerUI's tunnel
provisioning. Both are renderer/interaction work belonging to Phase 2–3, and a
speculative patch to library rendering code during a rebrand is worse than a
documented known failure.

**So: `yarn test` is not green.** 10 failures, all upstream, all reproducible in
isolation. This is the one Phase 0 exit criterion not met, and it is not met for
a reason that is documented rather than hidden.
